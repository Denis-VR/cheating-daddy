Главный приоритет — надёжность выделения вопросов и независимость распознавания от генерации. Затем стоит менять подачу: короткая опорная карточка, пример или схема, детали по запросу.

Это аудит, а не реализация исправлений. Исходный код приложения не изменялся.

## Что исправить

### P1. Распознавание блокируется генерацией ответа

Источник: `src/utils/hosted-ai.js:317`. Одна последовательная очередь обслуживает транскрипцию, ответы и изображения.

В отдельном локальном сценарии генерацию удерживали открытой, затем добавили аудио. Пока ответ не завершился: `transcribed=false`, в очереди одна задача. После завершения: `transcribed=true`, появился черновик. Сценарий использовал подставной ответ провайдера, а не измерение реальной сетевой задержки.

**Как исправить:** выделить очередь распознавания отдельно от очереди генерации; каждому сегменту дать номер и время захвата, сохранить порядок результатов. Отдельные отмена, таймауты и индикаторы для каждого процесса. Показывать возраст необработанной речи. При переполнении явно отмечать пропущенный интервал.

**Приёмка:** при искусственно задержанном на 30 секунд ответе новые реплики продолжают появляться; ответы не привязываются к чужим вопросам; отмена ответа не отменяет распознавание.

### P1. Разные вопросы склеиваются

Источник: `src/utils/interview-workflow.js:85`. Если реплики пришли с интервалом до пяти секунд и известная тема не противоречит предыдущей, они объединяются. Список тем содержит лишь несколько технических категорий. Время берётся при добавлении результата распознавания, а не при записи звука.

Воспроизведение: «Расскажите о прошлом проекте.» и через две секунды «Какие ваши зарплатные ожидания?» дают один черновик.

**Как исправить:** хранить исходные сегменты и реальные временные интервалы; различать продолжение, уточнение и новый вопрос. Сначала улучшить правила завершения предложений и начала самостоятельного вопроса; затем сравнить с классификатором на фиксированном наборе интервью. Добавить разделение/объединение именно черновиков вопросов; существующая работа с темами ответов — другой уровень.

**Приёмка:** независимые вопросы о проекте и зарплате разделяются; вопрос с паузой и его продолжение сохраняются вместе; задержки API не меняют границы вопросов.

### P1. Автоответ зависит от пунктуации и узкого списка слов

Источник: `src/utils/interview-workflow.js:22`. Прямой вызов `isAnswerCandidate` вернул `false` для:

- «В чем разница между процессом и потоком»;
- «Есть ли у вас опыт с Kubernetes»;
- «Приходилось ли оптимизировать запросы»;
- «Сравните TCP и UDP»;
- «Напишите функцию поиска».

С вопросительным знаком такие фразы проходят. Но реальная транскрипция в этой проверке уже показала пропуск `?`.

**Как исправить:** расширить формы русских и английских запросов; учитывать контекст и завершённость реплики. Неоднозначную реплику показывать с кнопкой «Ответить», а не молча игнорировать. Показывать причину ожидания: «жду продолжение», «нужно выбрать вопрос», «авторежим остановлен после ошибки».

**Приёмка:** фиксированный корпус вопросов без пунктуации, утверждений, подтверждений и уточнений; отдельно считать пропущенные вопросы и ложные срабатывания.

### P2. Постоянная задержка перед автоответом

Источники: `interview-workflow.js:28`, `hosted-ai.js:122`. Сейчас после тишины около 0,8 секунды требуется распознавание, затем ещё 5,5 секунды ожидания автоответа, затем генерация. Новые обновления очереди перезапускают ожидание.

**Как улучшить:** выбирать ожидание по завершённости реплики; добавить ручное «Ответить сейчас». Сначала измерять время конца речи, появления текста, решения об отправке и первого полезного ответа. Уменьшать задержку только вместе с проверкой преждевременных ответов.

### P2. Лента речи не является полной записью интервью

Источник: `CheatingDaddyApp.js:661`: последние 12 строк, каждая ограничена 600 символами. История ответов и восстановление черновиков существуют, но это не полный журнал произнесённого. Разбор строится по вопросам и подсказкам AI; он прямо предупреждает, что устные ответы кандидата не оценивались.

**Как улучшить:** при включённом пользователем сохранении вести локальный журнал текстовых сегментов с каналом, временем и связью с вопросом/ответом. Отдельно показывать речь кандидата и подсказку. Предусмотреть срок хранения и удаление. Для надёжного разбора не делать вывод о слабых знаниях только потому, что пользователь попросил пример.

## Более наглядный интерфейс

Сохранить короткий первый ответ, сворачиваемые подробности и отсутствие принудительного переключения на новый автоматический ответ. В открытом окне много равноценных элементов управления и широкие текстовые строки; вопрос, ключевая мысль и пример должны иметь более явный приоритет.

| Тип вопроса      | Что показывать первым                                                                             |
| ---------------- | ------------------------------------------------------------------------------------------------- |
| Определение      | Одна фраза + три опорных слова + один пример                                                      |
| Сравнение        | Таблица из 2–3 колонок, до 4 строк, с отличиями                                                   |
| Алгоритм         | Вход → шаги → результат; сложность отдельно                                                       |
| SQL              | Мини-таблицы исходных данных и результата запроса                                                 |
| System design    | Небольшая схема; ограничения и компромиссы рядом                                                  |
| Опыт / поведение | Четыре карточки STAR: ситуация, задача, действие, результат — только из подтверждённых материалов |
| Уточнение        | Что изменилось относительно предыдущего ответа                                                    |

Для deadlock вместо нескольких абзацев достаточно сначала показать:

`Поток A держит L1 → ждёт L2 → занят потоком B`

`Поток B держит L2 → ждёт L1 → занят потоком A`

Под схемой: «Цикл ожидания. Решение: единый порядок захвата блокировок».

Не заменять весь текст картинками: человеку всё равно нужна короткая фраза для собственного ответа. Схемы и таблицы должны пояснять именно этот вопрос. Для live-режима использовать готовые компоненты, а не генерировать тяжёлые изображения.

**Как реализовать:** модель отдаёт проверяемую структуру `kind`, `spokenSummary`, `keyPoints`, `example`, `caveats`, `sources`. Интерфейс выбирает шаблон. При невалидной структуре — обычный текст. Примеры, которые пользователь явно запросил, не прятать автоматически в «Углубиться». Уже существующие таблицы и диаграммы использовать повторно.

## Что есть у других решений

Проверены открытые официальные страницы, а не платные продукты в реальной работе. Маркетинговые обещания скорости и точности не считаются доказательством.

- [Final Round AI — live copilot](https://docs.finalroundai.com/docs/live-copilot/using-copilot): состояния «вопрос распознан», «жду продолжение», потоковый ответ, ручной запрос ответа, отдельная подача кода/схем. Полезно перенять ясные состояния и разделение устной подсказки и артефакта. Автоматическое исчезновение старого ответа при новом вопросе не стоит копировать без проверки удобства.
- [ParakeetAI](https://www.parakeet-ai.com/): распознавание и подсказки в разговоре, тренировочные интервью. Подтверждает наличие этого класса продуктов, но само по себе не доказывает превосходства над текущим приложением.
- [Yoodli — practice](https://support.yoodli.ai/en/articles/9550465-practice-with-yoodli): тренировка с уточняющими вопросами и последующим анализом. Полезный следующий шаг — повторить трудный вопрос голосом без подсказки и разобрать собственный ответ.
- [Metaview — interview notes](https://www.metaview.ai/interview-notes): структурированные записи интервью и сводки. Для этого приложения полезна связь «исходная реплика → вопрос → заметка», хотя основной пользователь Metaview — сторона найма.
- [OpenAI — VAD](https://developers.openai.com/api/docs/guides/realtime-vad): кроме определения пауз описано определение завершения реплики по смыслу. Это направление эксперимента для аудиопайплайна, не готовая замена текущему OpenRouter/Whisper-пути.

## Порядок работы

1. Независимая транскрипция, временные метки и регрессионные тесты на найденные ошибки.
2. Выделение вопросов и понятные состояния автоматического режима.
3. Карточки по типу вопроса; сначала сравнения, SQL и короткие схемы.
4. Полный текстовый журнал по выбору пользователя и тренировка по итогам сессии.

Перед выводом о готовности: повторяемый набор записей двух собеседников, паузы, шум, перебивания, отключение сети, ошибки API и длительная сессия. Измерять долю потерянных/склеенных вопросов, неверных автоотправок, задержку до полезной подсказки и сохранность после перезапуска. Целевые пороги задавать после исходного замера; текущие результаты не дают оснований обещать конкретную скорость или точность.
